# Architecture

## Public Native DSH Plugin Contract

The `0.1.0` distribution is one native DSH bundle with a Host service and Web Client. `packages/plugin/package.json` declares the Cordis patch, runtime exports, Web platform injection contracts, peer compatibility, and public release metadata. `DshSkillManagerService.Config` and the named `Config` export are the same Schemastery schema; all configurable filesystem roots are resolved by the Host, never supplied through browser RPC.

The Client owns two explicit runtime effects: the Typert Remote mount and its injected stylesheet. The `apply()` disposer releases both, and stylesheet ownership is counted on the DOM node so multiple loader generations do not remove a still-used sheet or leave a stale one behind. Slot registration continues through the platform-owned effect-aware `settings.section` API.

The source repository is an npm workspace, whereas the installable unit is `packages/plugin`. Therefore `v0.1.0` distributes a prebuilt plugin tarball and does not claim root-level GitHub source installation. Cross-Host `dsh-std` and dsh-TUI admission remain separate compatibility layers, not implicit properties of the native bundle.

## Current DSH Desktop v0.5.4 Adapter Boundary

The active Desktop integration is the same ordinary DSH Host/Web package used by standalone Harness. The Host registers the Protocol 5 Typert service, and the Client contributes one public `settings.section`; it does not import Desktop package-management services, Electron state, launcher internals, or platform DOM nodes. The exact local compatibility matrix is Harness/public runtime rc.2 plus UI primitives rc.7.

Navigation grouping is outside the plugin protocol. Skill Manager contributes the label `Skill 管理插件`; the installed optional settings-group companion recognizes `插件` and displays the entry under “高级”. This is a presentation outcome, not a new service dependency or installation authority. The feature panel still owns its `Skill 管理` title and folded-file artwork.

## Current Quota-Safe Source Policy

Local-to-GitHub provenance discovery is disabled at both Client and Host boundaries. The Client does not render automatic matching, bulk rematching, or per-Skill retry/status controls; the Host keeps the two provenance RPC descriptors only for wire compatibility and returns `PROVENANCE_MATCHING_DISABLED` before discovery. Capability protocol 5 reports `provenanceV2`, `batchProvenance`, and `skillsShDiscoveryHints` as false. Market/Host installation remains the trusted provenance writer, and only those registry records participate in GitHub update checks and updates.

Recent heat makes exactly two bounded Host-side HTML reads for weekly and monthly GitHub Trending and does not enrich cards through `api.github.com`. The resulting list may contain fewer than 20 entries because strong Skill/Agent filtering is applied to the global Trending page. Detail Inspection remains the point that resolves real repository metadata and a fixed commit. Installation can reuse the Host-owned resolution and codeload cache for one hour; it still performs complete snapshot, integrity, path, and risk validation before writing. Cache miss or expiry resolves normally, while update checks and updates keep latest-commit resolution.

Trending list candidates use `repositoryId: 0` and `ownerId: 0` as explicit unknown metadata until Inspection; the Typert wire schema accepts those sentinels, but any trusted repository/media/install path still requires authoritative Inspection data. Metadata-backed search candidates keep real positive GitHub IDs. Repository search has a 25-second abort-aware operation boundary so transient proxy/TLS setup does not fail at the previous 12-second threshold.

Completed bulk enable/disable/delete notices are Client-only transient state. They expose a 24px close control and clear after five seconds only if the same notice is still current; progress and errors use independent state and lifetimes.

## Dense Client Layout And Media Gallery

Managed Skill rows use four explicit layout regions: selection, file glyph, bounded copy, and actions. Desktop-width rows keep actions right-aligned; viewports below 520px place the action region on a deliberate second line spanning the content columns. This prevents optional update/delete controls from being auto-placed into the text column and keeps document overflow at zero.

Repository details retain a Client-side set of at most eight resolved media assets. The set is keyed by structured `MediaSource`, deduplicated, and loaded through the existing Host media proxy with at most three concurrent resolutions. Candidate Social Preview may render immediately; later manifest or same-repository fixed-commit README media is merged without allowing a failed response to clear an existing image. Browser decode failures remove only that asset. The gallery selection is presentation state and does not affect Inspection, risk, or installation decisions.

## Protocol 5 Repository Batches And Historical Matching Core

The Client negotiates capability protocol 5 and requires repository batch analysis/install plus Marketplace V2, risk, media, ranking, and classification capabilities. Local provenance discovery capability flags are deliberately false and are not market initialization requirements. Repository identity remains the discovery, display, download, and cache boundary. A Skill identity is the fixed GitHub numeric repository ID plus one `SKILL.md`-owning path; it is the unit eligible for installation, enablement, updates, or deletion. The fingerprint length-frames every sorted regular-file path and content, normalizes path separators plus UTF-8 CRLF/CR only, and preserves binary bytes, BOM, YAML order, and whitespace. The byte-exact `contentHash` remains separate for local-modification protection.

`cache/github-skill-index/v1.json` remains an atomically replaced verified-observation accelerator for manager-owned source records. The previous local candidate-matching engine and skills.sh hint adapter remain internal, disabled code paths pending a lower-cost redesign; public RPC never invokes them in the current build.

The compatibility `verifyProvenance` and `verifyProvenanceBatch` operations now terminate with `PROVENANCE_MATCHING_DISABLED` before any candidate search, fixed-commit resolution, or network work. Arbitrary local imports remain custom. Existing trusted registry sources and new market installs continue through the exact identity and update paths below.

Matched updates use GitHub numeric repository identity plus exact Skill path and the shared Snapshot Resolver. Repository rename/transfer updates the display slug, path basenames may differ from frontmatter names, and a missing path becomes `source-moved` rather than a guess. Changed snapshots carry static risk. Automatic update accepts only low/medium risk; high/unknown risk requires a manual second confirmation. The mutation refreshes the final commit and repeats complete integrity/risk checks before the existing backup, journaled atomic replacement, and target-link preservation.

## Components

1. **Core** owns validation, storage, discovery, repository inspection, snapshot resolution, media limits, static risk assessment, provenance, synchronization, updates, backups, 30-day recoverable deletion, and source adapters. It has no React, Electron, or Cordis dependency. Explicit provenance matching persists trusted source authority only for one exact complete-bundle match; matching names and descriptions alone never grant update authority. Trash restoration revalidates the bundle hash and every original target, while opportunistic cleanup deletes only valid manager-owned archives that are actually expired.
2. **DSH host plugin** exposes 24 typed RPC operations. Marketplace V2 separates metadata-only repository discovery, fixed-commit inspection, one-pass repository snapshot resolution, bounded media resolution, batch provenance, and atomic managed installation. `installRepository` rebuilds one current repository batch, then isolates every Skill outcome; it never accepts client-supplied commits, hashes, snapshots, or local paths. The v0.3.8 adapter targets `%DSH_HOME%/skills` for native DSH visibility and defaults external roots to `.codex/skills`, `.claude/skills`, `.agents/skills`, and OpenCode under the user home; explicit Host configuration may override each trusted root. Browser RPC never selects these paths or submits a trusted commit/hash. A pure handler layer depends on structural Core ports; the Cordis/Typert class is a thin runtime adapter. Core runtime code is bundled into the Host entry so standalone installation does not require a separately published Core package.
3. **DSH client plugin** negotiates capability protocol 5 before market traffic, mounts lightweight strict Remote descriptors, registers a dedicated settings section, and renders accessible React 18 interactions. The market home lists repository candidates from low-cost metadata and exposes `近期热度榜`, historical Stars, rolling-60-day creation, and relevance search. Recent heat retains the protocol-3-era `trend-monthly` wire value inside Protocol 5, ranks monthly candidates first, and renders weekly growth when known; `trend-weekly` remains a compatible Host wire capability rather than a separate Client control. Category controls use the 12-category candidate/Inspection model and never grant installation authority. The repository body opens a bounded 720px confirmation dialog portaled to `document.body`; the row `安装` action starts a silent all-install and opens that dialog only for high-risk confirmation. Local maintenance offers two default-off persisted options—update checks and updates—at most once per 24 hours; local source matching is hidden and forced off. Visible local Skills can be selected for bulk enable, disable, or 30-day recoverable delete. `同步到其他工具` remains a manual action for manager-owned Codex, Claude Code, Agents, and OpenCode links. `最近删除` lists recoverable records and restores them through Host validation. The UI maps surfaces and accents to DSH v0.3.8 theme aliases, and uses one 16×18 folded-file glyph. Full request/result validation and all mutation authority remain on the Host boundary.
4. **Desktop adapter** vendors the same standalone plugin, registers its companion layer in both v0.3.8 synchronization paths, and extends `patch-deps.js` only for exact `@deepseek-ai/dsh-client-ui-input-trigger@0.1.0-rc.6`. The per-session trigger controller caches names returned by each official candidate source and combines those names with the existing hot Skill lexicon, so another `/` is admitted only after a whitespace-bounded chain of observed command/Skill names. Only an empty query at the true leading position replaces a source snapshot; inline and filtered queries extend it, because rc.6 intentionally returns a narrower command roster inline. Source removal and disposal clear the corresponding cache. A manually typed command claim returned on Space becomes insertion of its source-provided canonical token, keeping prefix authoring in `plain`; a selection launched through the native `+ 命令` menu remains `claimed`, and Enter adjudication preserves native `/command arguments` claim/submit behavior. `@` keeps its original behavior. This remains a Desktop source adapter because rc.6 exposes only additive trigger-source registration and cannot replace native trigger detection.

## Leading Prefix

The portable authoring grammar uses whitespace-bounded tokens: `/command-one /skill-one /command-two body`. DSH's Host scans every matching user Skill gesture and injects Skills in first-seen order, so concatenating names without whitespace would lose content semantics. Known Skills and commands may continue the prefix. Once ordinary text or an unknown token starts, later slashes are not indexed. In v0.3.8 this does not create a multi-command transaction: the Host command parser owns only the first command and passes all following text to it as raw arguments.

## Storage

The default root is `%DSH_HOME%/skill-manager`:

- `library/`: canonical managed bundles;
- `active/`: fallback per-Skill links for direct core consumers that do not provide a DSH root;
- `registry.json`: versioned manager state;
- `backups/`: update rollback snapshots;
- `trash/`: complete recoverable snapshots of explicitly deleted manager-owned Skills, retained for 30 days when metadata and bytes remain valid;
- `cache/`: disposable remote index, cover data, and fixed-commit GitHub repository snapshots. `cache/github-snapshots` uses a 100 MB global LRU, one-hour last-access TTL, active leases, per-commit request coalescing, validated `.staging`, and atomic promotion. A repository snapshot is capped at 20 MB compressed, 50 MB extracted, 5,000 entries, 10 MB per file, and a 200:1 expansion ratio.

Writes use temporary sibling paths. Skill replacement first persists a complete bundle/registry backup and an atomic manager-owned journal, then swaps the canonical directory and commits the registry. On restart, strict old/new bundle hashes and the registry-selected hash recover only a known pre-commit or post-commit state; unknown or locally altered states stop for manual inspection. The manager never treats `.agents/skills` as its private canonical store because DSH scans that path by default.

## Trust Boundary

Remote repositories, archives, Markdown, images, and scripts are untrusted. Browse reads repository metadata only, so the Client can show the repository, publisher, avatar, social preview, Stars, Topics, and timestamps before repository content preparation finishes. Inspection fixes one commit, obtains one recursive Tree, then prefers one fixed-commit codeload ZIP for README, manifests, Skill frontmatter, and repository media. Every admitted ZIP or Raw-fallback byte sequence must match that Tree's declared size and Git blob SHA. Ordinary `tree/040000` entries describe directories and are ignored by bundle safety validation; repository-level symlinks are skipped and never exposed; a symlink, submodule, unsafe blob mode, or unknown entry inside a selected Skill rejects only that Skill. The Snapshot Resolver returns `ResolvedSkillSnapshot` values from one repository preparation; Core independently verifies identity, file metadata, complete Tree fingerprint, bytes, and canonical trimmed frontmatter name/description before staging. Immediately before the managed-library write, the Host refreshes the branch commit, resolves the exact final snapshot, and runs the static risk scanner synchronously; high-risk content requires an explicit acknowledgement. Installation never executes scripts, rejects unsafe cross-platform paths, and enforces bounded file counts/sizes. Root Skills are restricted to `SKILL.md`, `scripts/**`, `references/**`, `assets/**`, plus safe fixed-commit manifest-declared files; Agent instruction files remain excluded at every depth. Integrity and static content risk are displayed separately.

## Marketplace Sources

Marketplace V2 uses GitHub repository search and the experimental GitHub Trending HTML provider as its first browse surfaces. Format Topics seed discovery; category Topics classify already-discovered repositories. Listing never downloads README, Tree, `SKILL.md`, or media. Opening a repository invokes the GitHub Inspector, while installation invokes the Host-owned snapshot resolver and Core bundle verifier. Inspector, resolver, risk scanner, and same-repository media resolver reuse the same verified fixed-commit snapshot when available. This changes content cost from one REST blob request per document to a small metadata/commit/Tree REST baseline plus one codeload ZIP; it does not claim zero GitHub REST usage for Inspection. Recent heat itself makes only the weekly and monthly HTML requests and no per-card REST enrichment. Trending is full-site HTML data, not a stable official API; live, cached, unavailable, and empty states remain distinct.

The Host owns one proxy-aware marketplace fetch instance. When a proxy is required it reuses one keep-alive `HttpsProxyAgent`; every idempotent marketplace GET may retry known transient DNS/connect/TLS errors after 150 ms and 350 ms, but never retries non-GET work or cancellation. Inspection additionally limits document reads to three concurrent requests. The operation-level deadline still bounds the complete flow and caller cancellation aborts requests and retry delays.

Repository identity is `github:owner/repository`; Skill identity is `github:owner/repository#path`. Installation stores a deterministic fingerprint over every admitted regular file path, mode, blob SHA, and size. Read-only update checks compare the local byte-level bundle hash before networking, then compare the latest complete Tree fingerprint. Every deadline races an explicit rejecting boundary so an abort-ignoring transport cannot wait forever.

The separate `packages/index-schema` workspace freezes static catalog formats only. A central Indexer, historical trend calculation, signed index distribution, and GitHub Actions publication are deferred.

## Provenance And Update Authority

The only active GitHub provenance writers are source-aware market/Host installation and existing manager-owned registry migration/update paths. A user or AI copying files into a Skill directory does not establish repository identity, even if `SKILL.md`, name, or description points to GitHub. The historical candidate-matching engine remains in Core for possible redesign, but its public compatibility RPCs exit before invoking it. Updates address the recorded numeric repository ID plus exact Skill path and revalidate the latest complete fixed-commit bundle. Marketplace category controls dispatch metadata-only GitHub search and do not trigger local provenance work. Displayed type tags remain deterministic local derivations from name and description and do not rewrite `SKILL.md`. The historical v0.3.8 adapter replaced the rendered settings-row gear, but the current ordinary rc.2 Client does not touch platform-owned navigation DOM; folded-file artwork is limited to Skill Manager-owned content.

## DSH Enablement

The Harness Host adapter points the DSH target at the native `%DSH_HOME%/skills` root scanned by v0.3.8. Direct core consumers may instead omit `dshRoot` and use the private `active/` fallback. The manager discovers direct child bundles in Host-configured external roots and creates one per-Skill directory link for each explicitly enabled target. Exact existing manager links are idempotent; normal directories and links to other locations are conflicts and are never replaced. Disable removes only a link that still resolves to the canonical managed bundle. Existing roots and adjacent `AGENTS.md`/`CLAUDE.md` files remain untouched.
